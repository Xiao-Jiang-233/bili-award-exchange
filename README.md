# B站活动奖励自动领取（油猴脚本）

针对 B 站「奖励领取」页（`https://www.bilibili.com/blackboard/era/award-exchange.html?task_id=...`）的卡点抢领脚本。
默认 **23:59:00** 开始盯盘，任务状态一变「可领取」立刻自动点领取，失败按秒重试，成功后响铃并改标题提醒。

作者：[Xiao-Jiang-233](https://github.com/Xiao-Jiang-233)

## 安装

1. 浏览器装好 Tampermonkey（油猴）。
2. 打开 https://cdn.jsdelivr.net/gh/Xiao-Jiang-233/bili-award-exchange@main/bili-award-exchange.user.js ，油猴会弹出安装页 → 安装（脚本已带 `@updateURL` 指向 jsDelivr，以后我更新版本你那边会自动提示升级）。

> jsDelivr 对分支地址有缓存（约 12 小时）。刚推完新版本想立刻拿到，访问一次 `https://purge.jsdelivr.net/gh/Xiao-Jiang-233/bili-award-exchange@main/bili-award-exchange.user.js` 刷缓存，或在油猴里手动「检查更新」。
3. 登录 B 站后打开活动页（带 `task_id` 的那个地址），右上角出现面板即生效。

## 用法

- 打开页面即自动挂机到输入框里的时刻（默认 `23:59:00`，**按 B 站服务器时间**对时，不受本机时钟误差影响）。改完时刻按回车，再点「开始」重新挂机。
- 已经过了设定时刻才打开页面 → 立即开抢。
- **刚过 0 点打开**（距设定时刻不到 `POST_MIN`(默认 30) 分钟）→ 也立即开抢，而不是傻等到今晚 23:59：新一天的库存这会儿刚放出来，正是该抢的时候。
- 「开始 / 停止」按钮可随时手动接管；右上角「—」把面板收起。
- 抢到后：面板显示「领取成功」，铃声响，标题变成 `✅ ...`。奖励是站内私信/CDKey 的按页面提示去右上角「领奖记录」查看。

## 它做了什么

- 读 `/x/activity_components/mission/info` 判断状态：`0` 可领取、`1` 需绑定直播账号、`6` 已领取，其余为未完成/已领完。
- **抢的前提**：接口返回 `task_finished: true`（页面上那句「已完成任务」）才点领取；任务没达标只轮询不点。
- **库存只管「要不要收工」，从不挡点击**：点不点由服务端 `status === 0`（可领取）说了算。而且**卡点窗口**（开抢时刻起 `GRAB_MIN`(默认 10) 分钟内）**完全无视库存** —— 免得读到一个滞后的 0% 就把整晚收掉；窗口外（比如白天手动开始）才按库存收工。
- **每日库存已达上限**（`day_stock = 0`，即页面显示的「当日剩余量 0%」，或 message 提示）：今天已经领完 → **连续 `CAP_CONFIRM`(默认 3) 次都这么说才停**（防一次异常响应把整晚废掉）；
  - 注意**不要用 `day_remain_num` / `total_remain_num` 这两个"份数"字段**做判据：实测同一份响应里 `total_stock = 80`(%) 与 `total_remain_num = 0` 同时出现，这两个计数在非资格/未登录账号上恒为 0，用它当闸会永远不点或误判"已领完"。脚本只信页面自己也显示的那两个百分比字段。
- 面板的库存行直接显示**当日剩余 X%**（和活动页完全一致）；状态行会区分「等待放量」（库存 0%）和「有货但不可领：<原因>」（有货但资格/任务没到位）。**只有**距次日 0 点 `RESET_GRACE_MIN`(默认 30) 分钟内才不停，继续等 0 点刷新放量。
- **卡点盲点**（`BLIND = true`，持续 `BLIND_MIN` 默认 2 分钟）：从开抢时刻起**不等服务端状态**，先点下去再说 —— 手动连点就是这么抢的，而 0 点放量正好落在这一段里。盲点段结束后退回「`status === 0` 才点」。
- **点不快是有原因的**：页面自己的 `handleReceiveClick` 有 1 秒节流（lodash throttle 1000ms）**外加**请求在途屏蔽，所以任何方式（手动连点 / 脚本）都只能**1 秒 1 次**，再快也发不出去。脚本把**周期**设成 `CLICK_MS`(1000ms) 并扣掉本轮查询耗时，稳定贴着这个上限，每一下都真的发出去、不被吞掉。
- 点击的是页面自己的「领取」按钮 —— 复用页面自身的请求、签名和风控处理，不自己构造接口。
- 两次点击的周期 ≥1 秒（页面自身限流 1 秒 1 次），最多 `MAX_ATTEMPTS`(200) 次或 `MAX_MINUTES`(10) 分钟，超时自动停。
- 命中风控验证码（拖动/滑块/安全验证）时停止并提醒，验证码只能人工完成。
- **提示捕获不吃 CPU**：识别「领取成功 / 验证码」的 `MutationObserver` 挂在整个 `body` 上，但只扫「刚插入的小节点」（元素数 >8 的子树直接跳过）、攒批 300ms 扫一次、队列上限 200 —— 页面刷动画/列表也不会把主线程读卡。

## 点击节奏：贴着页面上限走

页面按钮被自身的 `throttle(handelReceive, 1000)` + 请求在途屏蔽锁死在 **1 秒 1 次**，这就是手动连点的天花板。默认策略是**顶到这个上限**：

- `CLICK_MS = 1000`：相邻两次点击的**周期**（不是间隔）扣掉本轮 `mission/info` 往返耗时后补到 1000ms，所以是稳定的 ~1 次/秒，而不是"1 秒 + 一次请求耗时"。
- 点击路径的抖动只剩 0~40ms（`JITTER` 的 ±50% 只作用于状态轮询），免得每一下被抖到 1.5 秒。
- 卡点窗口（`BLIND_MIN` 2 分钟）内不等状态、直接连点，0 点放量必然落在这段里。

## 注意

- **页面要留在前台别最小化**：浏览器会限制后台标签页的定时器，挂后台可能晚几十秒才触发。
- 活动规则写着「每日限量发放 153 份，先到先得」「请勿多次重复点击领取操作，会触发领取异常」—— 脚本已按状态判断后才点击、并限速，别把间隔参数改得太激进。
- 参数都在脚本头部：`POLL_MS`（轮询基准间隔）、`JITTER`（间隔抖动）、`CLICK_MS`（点击间隔）、`MAX_ATTEMPTS`、`MAX_MINUTES`、`MAX_FAILS`、`BACKOFF_MAX`。

## 遇到「受到神秘力量干扰，请稍后再试！」

这是 B 站风控（响应 `code: -351`，响应头 `bili-status-code: -351`），常见原因：**走代理/机场出口 IP 被标记**、请求过快、或 UA/Cookie 指纹异常。

- 先**关掉浏览器代理**（或让 `*.bilibili.com` 直连）再刷新页面 —— 实测同一台机器直连时该接口返回 `code: 0`，走代理时全部 `-351`，这种情况下脚本再快也没用。
- 脚本侧：查询失败会**指数退避**（1.5s → 3s → 6s … 上限 30s）并加 ±50% 抖动，连续 `MAX_FAILS` 次失败自动停止，不会继续加码风控。
- 不要为了「抢得快」把 `POLL_MS` 调到几百毫秒，风控是按「同一接口短时间被同一用户/IP/UA 多次请求」触发的。
- 换其它 `task_id` 的活动无需改脚本，`task_id` 从地址栏取。
